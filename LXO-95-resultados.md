## 1. Orquestador unificado

El cambio autorizado está implementado en este checkout: Orquestador tiene un solo navegador, sin pestañas paralelas «Ejecuciones» y «ADE». LXO-95 solo conserva el shell y la integración mínima de Queries existentes; no reconstruye el navegador completo de Projects/Tasks.

```text
Orquestador
├─ Projects → Tasks del Core
├─ Operación → Runs, tareas hijas, aprobaciones y atención operativa existente
└─ Canvas contextual → Workspace ADE o workspace operativo del Run seleccionado
```

Projects y Tasks usan `project_id`/`task_id` durables de Core y estado de selección propio. Runs legacy permanecen en Operación sin Project inferido. La selección de un target cambia el canvas central; alternar entre Task ADE y Run mantiene montados ambos canvases. AgentPanel, PTYs y vistas operativas siguen en el canvas oculto. El canvas de Task solo consulta y muestra información; no ofrece creación de Tasks/Attempts ni añade acciones operativas.

La sección Operación conserva deliberadamente el árbol de Runs y sus acciones preexistentes (incluido quitar Run), aprobaciones de spawn, atención operativa y acceso a Actividad/Cambios/terminal según el target. No se activaron esas acciones durante la validación. La vista de Core Task no tiene mutaciones. La lista de atención operativa no es un Inbox global; LXO-89 ya provee queries autoritativas y LXO-100 es responsable de integrar Inbox, filtros, contadores, tarjetas y navegación global en Desktop. F2 no presenta datos ni controles de Attention simulados.

La navegación visible actual conserva el listado de Tasks activas que ya consume `tasks_by_project(active)`. El cambio no añade filtros ni una vista nueva para Tasks finalizadas: LXO-97 completará la exploración que distingue activas/finalizadas, y LXO-98 el detalle read-only ampliado. Las Queries `active`, `final`, `all` y `task_detail` sí se comprobaron en Core aislado con datos propios de ese entorno.

## 4. Agregar clientes/proveedores: causa y destino

La operación no tiene un único registro “cliente/proveedor”. Se distinguen cuatro capas:

1. **Identidad de cliente Core/Desktop/CLI.** Desktop crea/provisiona su identidad local automáticamente al necesitarla (`client_identity.rs`); LXO-85/LXO-86 cubrieron identidad y autenticación de CLI. No se encontró un control Desktop para registrar manualmente más identidades cliente. El rechazo de autenticación CLI del perfil aislado es un problema de credencial/identidad, distinto de la falta de alta de providers.
2. **Agregar un provider adapter.** El registro de providers en Desktop viene del inventario del host y de adapters conocidos; no hay un flujo de UI para registrar un provider arbitrario. El selector de RolesSettings filtra disponibilidad/bloqueo y el catálogo `+ Nuevo` es fijo.
3. **Abrir sesión.** La ruta de inicio depende del tipo conocido de engine (Claude abre chat; Codex usa launcher/PTy). La apertura de sesión no añade un cliente ni instala/configura un adapter.
4. **Perfil Codex deshabilitado.** Un perfil bloqueado por la política de sandbox es disponibilidad del perfil, distinta de identidad Core, registro de provider o creación de sesión.
